Linux CPU 排程器演進

Linux 的 CPU scheduler 從 2.4 一路演進到 6.12，每一代到底是怎麼決定「下一個該由哪個 task 使用 CPU」的？又為什麼要一再改寫？這個網站把同一組工作負載丟給不同年代的 CPU scheduler，並排比較它們的行為，每一次排程決策都可以點開來看理由，並對照當年的 kernel 原始碼。

試想一個情境：你一邊用 make -j 編譯 kernel，一邊聽音樂、在編輯器裡打字。編譯會吃掉所有拿得到的 CPU，但音樂不該斷，按下按鍵後字也該立刻出現。能不能做到，取決於 CPU scheduler 怎麼在這幾個 task 之間取捨。

為什麼要了解 CPU scheduler

要弄懂 CPU scheduler 怎麼運作，幾乎會碰到作業系統課本的每一章：process 的狀態與 task_struct、驅動 tick 的 timer interrupt、context switch 與 preemption（以及哪些區段不能被搶占）、保護 runqueue 的 lock、為了常數時間挑選而設計的資料結構（O(1) 的 bitmap、CFS 的紅黑樹、EEVDF 的 augmented 紅黑樹），再往外延伸到多核的 load balancing、cache 與 NUMA 的區域性，以及省電。換句話說，讀懂 CPU scheduler，等於把這些觀念放在同一個真實的系統裡重新串起來。

一個 task 經過的時間，可以拆成真正在 CPU 上執行的時間，以及想執行卻在 runqueue 裡等待的時間，後者完全由 CPU scheduler 決定。Linux 在 /proc/<pid>/schedstat 裡分別記錄這兩者，perf sched latency 也能列出每個 task 被喚醒後等了多久。對伺服器而言，真正讓使用者感到卡頓的往往是 p99 這類尾端延遲，而處理 request 的 thread 被喚醒後要等多久才能執行，正是 CPU scheduler 的責任；反過來說，頻繁切換 task 雖然能降低延遲，卻會增加 context switch 的成本、破壞 cache 的區域性，讓吞吐量下降。不了解 CPU scheduler 在這兩端之間怎麼取捨，看到這些數字也很難判斷問題出在哪裡。

CPU scheduler 是作業系統裡理論與工程交會得最明顯的地方之一：比例分享（proportional share）有乾淨的數學模型，EEVDF 甚至出自 1995 年 Stoica 與 Abdel-Wahab 附有證明的論文；但 kernel 的實作必須面對整數運算、tick 的粒度、各式各樣的工作負載，以及「不能讓既有使用者變慢」的壓力。逐一比較理論模型和 kernel 實作的落差，是理解這些工程取捨最直接的方式。

為什麼 Linux 一再改寫 CPU scheduler

每一次大改，都是為了解決前一代暴露出的問題：task 一多，挑選的成本就失控；用 heuristics 猜測誰是 interactive，卻被輕易騙過；只追求公平，又無法表達延遲的需求。點選時間軸上的各代看設計重點。

回頭看這條路線

O(1) 以前，CPU scheduler 靠 heuristics 猜測哪些 task 是 interactive；CFS 放棄猜測，只追求公平，再用喚醒補償粗略地照顧 interactive task；EEVDF 則把公平與延遲拆開，並在 v6.12 讓 task 自己表明需求。lag 這個量的命運也很有意思：v2.6.23 的 wait_runtime 直接記錄 lag，v2.6.24 改用 vruntime 後它不再明確存在，到了 v6.6 又以 vlag 的形式回來。

    系統只有一顆 CPU，上面同時有好幾個 task（執行中的程式，以下都用 task 稱呼）。任何時刻只有一個 task 能在 CPU 上執行，其他想執行的 task 只能在 runqueue 裡排隊；還有一些 task 正在等待鍵盤輸入、磁碟或計時器，處於 sleep 狀態，暫時不需要 CPU。

    那麼該挑誰呢？這取決於 task 需要什麼。像播放音樂、文字編輯器這類 interactive 的 task，平常大多在 sleep，每次醒來只用一點點 CPU，但必須馬上得到執行，否則就會聽到斷音、看到畫面卡頓，因此它們在意的是延遲（latency）。相對地，編譯這類 CPU-bound 的 task 永遠有事可做，晚個幾毫秒執行並無所謂，它們在意的是一段時間下來是否拿到公平的 CPU 份額。

    麻煩的是，這兩種需求會互相拉扯：讓音樂播放器插隊固然降低了延遲，但它插隊所用的時間，其實是從編譯 task 那裡拿走的。接下來幾章先把「公平」定義清楚，再看各代 CPU scheduler 怎麼回答：O(1) 用優先權加時間片，從行為猜誰需要快速回應；CFS 和 EEVDF 先保證公平，再在公平之上處理延遲。

    要談公平，得先定義每個 task 應該分到多少。Linux 讓使用者用 nice 值（−20 到 19）表達優先程度，nice 越小越優先。kernel 用 prio_to_weight[] 這張表把 nice 換成權重 w，表的設計是 nice 0 對應 1024，每差一級約差 1.25 倍：

    w(\text{nice}) \approx \frac{1024}{1.25^{\,\text{nice}}}

    例如 nice 5 是 1024 / 1.25^5 \approx 335，nice −5 是 1024 \times 1.25^5 \approx 3121（表裡存的是取整後的值）。有了權重，公平就能寫成一條式子：task i 應得的 CPU 比例是

    \text{share}_i = \frac{w_i}{W}, \qquad W = \sum_{j \,\in\, \text{runnable}} w_j

    W 只加總想執行（runnable）的 task。sleep 中的 task 不算在內，所以有 task 睡著時，其他 task 的比例會跟著變大。下圖預設的 A、B、C 是 nice −5、0、5，A 應得

    \text{share}_A = \frac{3121}{3121 + 1024 + 335} = \frac{3121}{4480} \approx 69.7\%

    理想情況下，想執行的 task 會「同時」以各自的比例前進，就像水流同時分給幾根管子。這個假想的模型稱為 GPS（Generalized Processor Sharing）。在 GPS 裡，經過時間 t，task i 應該拿到的 CPU 時間是（假設這段期間想執行的 task 沒有變）

    S_i = \frac{w_i}{W}\, t

    真實的 CPU 一次只能執行一個 task，CPU scheduler 只能讓它們輪流執行。把 task i 實際拿到的時間記為 s_i，兩者的差就是 lag：

    \text{lag}_i = S_i - s_i

    lag 為正，表示 CPU scheduler 欠它；為負，表示它多拿了。舉個例子：三個 nice 0 的 task 都想執行，CPU scheduler 讓 A 連續跑 1ms。這 1ms 內 GPS 會給每個 task \tfrac{1}{3} ms：

    taskS_i（GPS 應給）s_i（實際）\text{lag}_i = S_i - s_i
    A\tfrac{1}{3} ms1 ms-\tfrac{2}{3} ms
    B\tfrac{1}{3} ms0+\tfrac{1}{3} ms
    C\tfrac{1}{3} ms0+\tfrac{1}{3} ms

    接著換 B 跑 1ms、再換 C 跑 1ms。每過 1ms，跑的那個 lag 減 \tfrac{2}{3}，等的兩個各加 \tfrac{1}{3}。到 3ms 時三個 task 各跑了 1ms，剛好等於 GPS 給的，lag 全部回到 0。

    模擬頁每個 CPU scheduler 底下的那張圖，畫的就是這個量。看圖時要分辨一時的鋸齒和長期的漂移：鋸齒是輪流執行必然的結果，一條線如果一路往下、沒有回來，才表示那個 task 長期拿得比公平的份多。

    深入：想執行的 task 會變時，GPS 怎麼定義

    上面的 S_i = \frac{w_i}{W} t 假設 W 不變。一般的定義是用速度來寫：時刻 \tau 所有想執行的 task 權重加起來是 W(\tau)，task i 這一刻拿到 CPU 的速度是

    \frac{dS_i}{d\tau} = \begin{cases} \dfrac{w_i}{W(\tau)} & i \text{ 想執行} \\[6pt] 0 & i \text{ 在 sleep} \end{cases}

    把速度從 0 積到 t，就是 GPS 到時刻 t 為止會給 i 的 CPU 時間 S_i(t)。task 在 sleep 時 GPS 不分 CPU 給它，S_i 和 s_i 都不動，所以 lag 停在睡前的值，醒來接著算。這是一個選擇，不是唯一的算法；會看到 CFS 和 v6.12 在這裡的做法不一樣。

    深入：為什麼是鋸齒，鋸齒能有多高

    把定義對時間微分。GPS 給的速度是 w_i / W；真實的 CPU scheduler 給的速度不是 1 就是 0，看 task 在不在 CPU 上。所以想執行的 task，lag 的斜率只有兩種：

    \frac{d\,\text{lag}_i}{dt} = \frac{w_i}{W} - \frac{ds_i}{dt} = \begin{cases} \dfrac{w_i}{W} - 1 & i \text{ 在 CPU 上} \\[6pt] \dfrac{w_i}{W} & i \text{ 在排隊} \end{cases}

    三個 nice 0 時 w_i / W = \tfrac{1}{3}，跑的那個以 -\tfrac{2}{3} 的斜率往下，等的兩個以 +\tfrac{1}{3} 往上。換人執行，斜率就翻過來，所以每條線都是一段一段的折線。

    鋸齒的高度取決於 CPU scheduler 一次讓一個 task 連續執行多久。task 連續執行 q，lag 就下降 q\,(1 - w_i/W)。兩個 nice 0 的 task 輪流，每次跑 10ms，lag 一次擺 10 \times \tfrac{1}{2} = 5 ms；每次只跑 1ms，就只擺 0.5ms。後面會看到，CFS 一次讓 task 跑一整段，EEVDF 一次只跑一個很短的 slice，兩者的鋸齒高度差了一個量級，EEVDF 的論文還證明了 lag 的上下界（）。

    深入：為什麼所有 lag 加起來永遠是 0

    只要有 task 想執行，真實的 CPU scheduler 和 GPS 都不會讓 CPU 閒著，所以同一段時間兩邊發出去的 CPU 總量一樣多。把所有想執行的 task 加起來：

    \sum_i \frac{dS_i}{dt} = \sum_i \frac{w_i}{W} = 1, \qquad \sum_i \frac{ds_i}{dt} = 1 \quad\Longrightarrow\quad \frac{d}{dt}\sum_i \text{lag}_i = 0

    sleep 中的 task 兩邊都是 0，lag 不動，也不影響總和。一開始大家的 lag 都是 0，所以總和永遠是 0：有人多拿，就一定有人少拿。因此看圖時不能只看一條線，audio 往下多少，cc1 和 cc2 合起來就往上多少。會看到，EEVDF 的 V 正是靠這個性質算出來的。

    有了衡量公平的尺，但 Linux 的 CPU scheduler 一開始並不是照比例分配 CPU 來設計的。2.6 的 O(1)（Ingo Molnar，2002 年）比較接近作業系統課本上的優先權排程：每個 task 有一個優先權和一段時間片（time slice），先挑優先權最高的，讓它跑完時間片再換人。這一章看它怎麼挑、怎麼分時間片，以及怎麼照顧 interactive task。

    名字裡的 O(1)

    先看它取代的 2.4（O(n)）。2.4 每次 schedule() 都把 runqueue 上的 task 全部走過一遍，用 goodness() 打分數，挑最高的：

    \text{goodness}_i = \text{counter}_i + 20 - \text{nice}_i

    counter 是剩下的時間片（以 tick 計），用完時 goodness 是 0，不會被挑。runqueue 上有 n 個 task，每次挑選就要算 n 次；所有 runnable task 的 counter 都用完時，還要走過系統上的每一個 task 重新發時間片。task 一多，CPU scheduler 自己就成了負擔。

    O(1) 把 140 級優先權各放一條佇列，再用一個 140 位元的 bitmap 記錄哪幾級有 task。數字越小越優先，挑選就是找第一個非空的佇列，取它的隊首：

    p^{*} = \min\{\, p \mid \text{queue}[p] \ne \varnothing \,\}

    這一步由 sched_find_first_bit() 在 bitmap 上找第一個 1，步數固定，和 task 有幾個無關，這就是名字裡的 O(1)。

    task 多了會怎樣

    讓 runqueue 上有 n 個一直要 CPU 的 task，量每次 schedule() 做了幾次比較。這裡的「一次」是模擬器的成本模型：算一次 goodness()、查一次 bitmap、在紅黑樹上走一層，各算一次。

    \text{cost}_{2.4} \approx n + 1, \qquad \text{cost}_{2.6.0} = 1

    2.4 多出來的那一次是 prev。prev 還想跑時，先拿它當候選算一次 goodness，接著走整條 runqueue，而 prev 本身也在 runqueue 上。重算時間片的 for_each_task 也是 O(n)，但大約每 n 次挑選才發生一次，攤提下來每次只多一點。2.6.0 把「時間片用完、排到下一輪」的搬移放在 scheduler_tick() 裡做，schedule() 本身只剩查 bitmap。

    橫軸每一格 task 數翻一倍。2.4 的成本跟著翻倍，所以線越往右越陡；2.6.0 是一條平線。按「放大」看後來的 CFS 和 EEVDF：它們把 task 放在紅黑樹上（），成本隨 \log n 成長，每翻一倍只多一兩層，在這張圖上是直線。CFS 挑選時直接取快取的最左節點，成本花在把 prev 插回樹、把 next 拿出來；EEVDF 的 pick_eevdf() 要往下走樹，找 eligible 之中 deadline 最早的，所以挑選本身也隨 \log n 成長。

    成本模型只數比較與走訪節點的次數，不是 CPU 時間。真實的 2.4 還有兩項成本本站沒有模擬：每走過一個 task 就要讀它的 task_struct，cache miss 隨 n 增加；多核時整條 runqueue 共用一把 lock。工作負載也是最壞的情況，n 個 task 全都 runnable，一般桌面上同時 runnable 的 task 不多。

    深入：2.4 的 counter 也偷偷照顧了 sleeper

    2.4 重新發時間片時，用 for_each_task 走過系統上所有 task，連 sleep 中的也算：

    \text{counter} \leftarrow \left\lfloor \frac{\text{counter}}{2} \right\rfloor + T, \qquad T = \texttt{NICE\_TO\_TICKS}(\text{nice})

    CPU-bound 的 task 每次都把 counter 用到 0，重算後就是 T。一直在睡的 task 用不完，每次重算保留一半再加 T，會逼近不動點 c = c/2 + T，也就是 c = 2T。counter 越大 goodness 越高，所以 sleeper 醒來時大多能排在 CPU-bound task 前面，但多出來的最多就是一個時間片。

    兩輪：active 與 expired

    每個 runqueue 有兩個 prio_array。CPU scheduler 只從「這一輪」（active）挑。task 用完時間片時，scheduler_tick() 重算它的時間片和 prio，把它排到「下一輪」（expired）。等這一輪空了，schedule() 把兩個指標對調，下一輪就開始。對調指標是常數時間，所以 O(1) 不必像 2.4 那樣走過所有 task 重發時間片。

    如果 task 都是 CPU-bound，也都沒被當成 interactive，每一輪每個 task 各跑一次自己的時間片，分到的比例就是時間片的比例：

    \text{share}_i = \frac{\text{slice}_i}{\sum_j \text{slice}_j}

    例如 nice 0 和 nice 5 各一個，nice 0 分到 102 / (102 + 78) \approx 56.7\%。的權重算出來是 1024 / (1024 + 335) \approx 75.3\%。同一組 nice 值，兩代 CPU scheduler 給的比例差很多，下一章會回來看這件事。

    先按幾次「跑一個時間片」，看 A、B、C 怎麼從這一輪移到下一輪，以及這一輪空掉時的對調。接著讓 C 被判定為 interactive，按「跑 30 個」，看 A、B 等了多久才又輪到。

    照顧 interactive task：sleep_avg 與 bonus

    只看 nice 的話，editor 醒來得排在同一級的編譯 task 後面，可能要等上一整個時間片（102ms），打字就會卡。O(1) 沒有讓 task 表明「我需要快速回應」的介面，只能從行為猜：常常在睡的，大概就是 interactive。每個 task 有一個 sleep_avg（0 到 1020ms），睡覺時加、在 CPU 上跑時扣，再換算成 bonus：

    \texttt{CURRENT\_BONUS} = \left\lfloor \frac{\texttt{sleep\_avg} \times 10}{1020} \right\rfloor, \qquad \text{bonus} = \texttt{CURRENT\_BONUS} - 5, \qquad \texttt{prio} = \texttt{static\_prio} - \text{bonus}

    bonus 介於 −5 到 +5。nice 0 的 task，sleep_avg 滿了是 prio 115，一直在跑的是 prio 125。這個 prio 有兩個用處：

    • 喚醒時，醒來的 task 的 prio 比目前在跑的小，就搶占它（TASK_PREEMPTS_CURR）。editor 醒來能打斷編譯，靠的就是 bonus。
    • 時間片用完時，夠 interactive 的 task 排回這一輪，不用等下一輪。條件是 TASK_INTERACTIVE：
    \texttt{prio} \le \texttt{static\_prio} - \Delta(\text{nice}), \qquad \Delta(0) = 2

    nice 0 時就是 bonus ≥ +2，也就是 CURRENT_BONUS ≥ 7、sleep_avg ≥ 714ms。nice 越大 \Delta 越大，越難被當成 interactive；nice 19 永遠不會。上面小圖裡「讓 C 被判定為 interactive」就是第二條：C 在 prio 118，每次跑完時間片都排回這一輪，A、B 在 prio 125，只能一直等。

    深入：EXPIRED_STARVING，給 starvation 的保險

    interactive task 可以一直留在這一輪，其他 task 就可能一直輪不到。scheduler_tick() 在讓 interactive task 排回這一輪之前，會先檢查 EXPIRED_STARVING()：

    \text{now} - \texttt{expired\_timestamp} \;\ge\; \texttt{STARVATION\_LIMIT} \times \texttt{nr\_running} + 1

    expired_timestamp 是這一輪第一次有 task 用完時間片的時刻，兩輪對調時歸零。STARVATION_LIMIT 是 1020 個 jiffy（約 1 秒），條件成立後，interactive task 用完時間片也得去下一輪。2.6.0 kernel/sched.c 的註解寫的是 “To guarantee that this does not starve expired tasks we ignore the interactivity of a task if the first expired task had to wait more than a 'reasonable' amount of time”。這是作業系統課本上 aging 的一種：等太久，優待就取消。不過門檻和 task 數成正比，三個 task 要等約 3 秒，對延遲來說已經很長。

    簡化：小圖裡三個 task 都不睡覺，C 的 bonus 是直接給的；實際上 sleep_avg 每跑一點就扣一點。也沒有畫 TIMESLICE_GRANULARITY：interactive task 的時間片會切成小段，跑完一段就排到同一級的隊尾，和同一級的 task 輪流。

    O(1) 解決的是 2.4 的成本問題，這件事它做得很好。它被換掉，原因在上一章的最後一節：它得猜誰是 interactive。這一章先算出它怎麼被騙，再看為了防騙補上的規則，最後是 2007 年 CFS 登場時怎麼說。

    sleep_avg 怎麼加、怎麼扣

    task 醒來時，recalc_task_prio() 把睡眠時間 s 加進 sleep_avg，但先乘上一個倍數，sleep_avg 越低，倍數越大：

    \texttt{sleep\_avg} \leftarrow \min\bigl(1020,\; \texttt{sleep\_avg} + s \times (10 - \texttt{CURRENT\_BONUS})\bigr)

    （CURRENT_BONUS 是 10 時倍數取 1。）在 CPU 上跑的時間 r，schedule() 照實扣掉：

    \texttt{sleep\_avg} \leftarrow \max(0,\; \texttt{sleep\_avg} - r)

    kernel 的註解是 “The lower the sleep avg a task has the more rapidly it will rise with sleep time.”。用意是讓剛從 CPU-bound 轉成 interactive 的 task，例如編譯完回到提示字元等鍵盤的 shell，很快就能拿回 bonus。睡 1ms 最多能抵 10ms 的執行時間，這個不對稱就是可以利用的地方。

    用掉 75% 的 CPU，還算 interactive

    一個 task 重複「跑 r、睡 s」。CURRENT_BONUS 是 b 時，一次睡眠加 s\,(10 - b)，一次執行扣 r。加的比扣的多，sleep_avg 就往上爬；爬到加的不再比扣的多，就停住。打平的地方是

    s\,(10 - b) = r \quad\Longrightarrow\quad b^{*} = 10 - \frac{r}{s}

    CURRENT_BONUS 是整數，所以 sleep_avg 會卡在 \lceil b^{*} \rceil 那一級的下緣上下擺動：剛睡醒時在 \lceil b^{*} \rceil，跑著跑著掉到 \lfloor b^{*} \rfloor。時間片多半是在跑的時候用完的，那時要 \lfloor b^{*} \rfloor \ge 7（上一章 nice 0 的 bonus ≥ +2）才能留在這一輪：

    10 - \frac{r}{s} \ge 7 \;\Longleftrightarrow\; r \le 3s \;\Longleftrightarrow\; \frac{r}{r + s} \le 75\%

    也就是說，只要每跑 3ms 至少睡 1ms，一個用掉四分之三 CPU 的 task 也能享有 interactive 的全部優待。醒來時的門檻更鬆：只要 \lceil b^{*} \rceil \ge 7，也就是 r < 4s，用掉不到 80% 的 task 睡醒時都算 interactive。情境 3 的 cheat 每跑 2.3ms 睡 0.83ms，r/s \approx 2.77，b^{*} \approx 7.23，在 7 和 8 之間擺動，兩個門檻都過了。

    按「cheat」，再把「每次睡」慢慢拖小：低於 0.77ms（2.3 / 3）時，跑到一半就會掉出 interactive 的區域；低於 0.58ms（2.3 / 4），連剛睡醒時也不算了。按「跑 3、睡 0.8」看兩者之間的情況：r/s = 3.75，剛睡醒時 bonus +2，跑著跑著掉到 +1。

    2007：不再猜

    2007 年 Con Kolivas 提出 RSDL（後來改名 SD，Staircase Deadline），不估計 interactivity，只靠公平的規則，桌面的反應一樣好。同年 4 月，Ingo Molnar 發表 CFS，公告裡說：

    Thus the CFS scheduler has no notion of 'timeslices' and has no heuristics whatsoever.

    他也說 CFS “has no 'array switch' artifacts (by which both the vanilla scheduler and RSDL/SD are affected)”，並把方向歸功給 Kolivas：“he has proven via RSDL/SD that 'fair scheduling' is possible and that it results in better desktop scheduling. Kudos Con!”

    CFS 在 2.6.23（2007 年 10 月）合併，sleep_avg、bonus 和兩輪都不見了。它改用的思路：照權重分配，記錄每個 task 跑了多少。interactive task 睡覺時沒有在跑，自然會落後，醒來就自然會被選中，不用猜。下一章看這件事怎麼寫成 vruntime，以及這個「自然」為什麼也需要一道上限。不過，會看到，CFS 後來也慢慢長出自己的 heuristics。

    上一章的結論是：猜誰是 interactive，就會被騙。CFS 乾脆不猜，只量每個 task 跑了多少。它的做法是替每個 task 記錄一個 virtual runtime（vruntime，以下記為 v_i）。task 每執行 \Delta t，update_curr() 就把它的 vruntime 加上

    \Delta v_i = \Delta t \times \frac{1024}{w_i}

    也就是實際執行時間除以「權重是 nice 0 的幾倍」（w_i / 1024）。同樣執行 1ms：

    nicew_i1024 / w_i執行 1ms，vruntime 增加

    挑選的規則只有一條：選 vruntime 最小的 task。

    \text{pick} = \mathop{\arg\min}_{i} \; v_i

    權重小的 task 執行一下 vruntime 就跑到前面去，得等其他 task 追上來才會再輪到它。長期下來每個 task 的 vruntime 會彼此貼近，而 vruntime 相等正好就是公平。從 0 開始累計時 v_i = t_i \times 1024 / w_i（t_i 是實際執行時間），所以

    v_A = v_B \;\Longrightarrow\; \frac{1024\, t_A}{w_A} = \frac{1024\, t_B}{w_B} \;\Longrightarrow\; \frac{t_A}{t_B} = \frac{w_A}{w_B}

    sleep 帶來的問題

    task 在 sleep 時不執行，vruntime 也停住不動，其他 task 的 vruntime 卻繼續往前走。假設 A 睡了 T，這段期間有 n 個 nice 0 的 task 平分 CPU，每個拿到 T/n，vruntime 也各前進 T/n。A 醒來時落後

    \Delta v = \frac{T}{n}

    若照規則直接挑 vruntime 最小的，A 醒來後只要還有事做，每次都會被選中，直到追上為止。例如三個編譯 task 在跑，A 睡了 3 秒，醒來時落後 3/3 = 1 秒；如果 A 醒來後是一段 CPU-bound 的計算，三個編譯 task 就得整整停住 1 秒。睡得越久，其他 task 停得越久，而且沒有上限。這種「想執行，卻長時間拿不到 CPU」的情況稱為 starvation。

    CFS 的做法是限制醒來時落後的幅度。喚醒時 place_entity() 重新安排它的 vruntime：

    v_i \leftarrow \max\bigl(v_i,\; \texttt{min\_vruntime} - 20\,\text{ms}\bigr)

    min_vruntime 大致是 runqueue 上最小的 vruntime，20ms 是 sysctl_sched_latency。取 max 的效果分兩種情況（數值以 min_vruntime 為 0）：

    醒來時的 v_i候選位置放回的位置
    只睡一下−5 ms−20 ms−5 ms（不變）
    睡了很久−60 ms−20 ms−20 ms（被拉上來）

    不管睡了多久，醒來的 task 最多只領先 min_vruntime 20ms，所以它一次能「討回」的 CPU 有了上限，其他 task 不會再被餓上一整秒。換個角度看，這 20ms 是給 sleeper 的補償，interactive task 醒來後通常因此能立刻搶占；代價是它分到的 CPU 可能比公平的份額還多，而睡前被欠的、超過 20ms 的部分則直接一筆勾銷。

    深入：starvation 與 aging，其他 CPU scheduler 怎麼處理

    避免 starvation 是 CPU scheduler 的基本要求之一：每個 runnable 的 task 終究要被執行，而且等待的時間要有上限。starvation 常出現在下面這類挑選規則：

    • 嚴格的優先權排程：只要還有高優先權的 task 想執行，低優先權的 task 就永遠輪不到。
    • SJF（Shortest Job First）：短工作源源不絕地進來時，長工作會一直被往後排。
    • 挑「被虧欠最多」的 task，但虧欠沒有上限：就是上面 vruntime 的情況。被虧欠的一方一次把帳討回來，其他 task 在這段期間被餓著。

    作業系統課本上的典型解法是 aging：task 等得越久，優先權就逐漸提高，最後一定輪得到。O(1) 的 EXPIRED_STARVING() 是同一類的做法（）：下一輪等太久，就取消 interactive task 的優待。CFS 不需要這種保險，等著的 task vruntime 不動，遲早會變成最小的；它要處理的是反方向的問題，也就是醒來的 task 落後太多。

    簡化：小圖每 1ms 重新挑選一次。實際的 CFS 會讓 task 跑完一段 sched_slice() 才切換，被喚醒的 task 也要落後超過一定門檻才會搶占（）。

    先說清楚「離開」的範圍。v6.6 換掉的是 CFS 挑選、放置與搶占的規則，sched_entity、vruntime、紅黑樹、kernel/sched/fair.c 和 cgroup 的群組排程都還在；被拿掉的是「選 vruntime 最小的」這條規則，以及外面那一圈為了照顧延遲而長出來的 heuristics。

    問題也不在公平。上一章推過，vruntime 相等就是公平，本站情境 5 量到的 CPU 比例和理論值相差不到 0.01%。CFS 的麻煩在於延遲沒有正式的位置，以下照 mailing list 上的討論，把理由一個一個拆開來看。

    只有一個參數：權重

    Peter Zijlstra 在合併進 kernel 的 EEVDF commit 裡，第一句話就是：

    Where CFS is currently a WFQ based scheduler with only a single knob, the weight. The addition of a second, latency oriented parameter, makes something like WF2Q or EEVDF based a much better fit.

    回頭看的式子，CFS 裡 task 唯一能影響的是 vruntime 前進的斜率：

    \Delta v_i = \Delta t \times \frac{1024}{w_i}

    nice 改變的是 w_i，也就是長期能拿到多少 CPU，而不是醒來後多快能執行。LWN 的說法是 “nice values (priorities) can be used to give a process more CPU time, but that is not the same thing.”。試想一個 audio task，它每 5ms 只需要一點點 CPU，但要準時；把它的 nice 調低，它會拿到更多用不完的份額，延遲卻沒有直接的保證。EEVDF 多了第二個參數 r_i（request，也就是 slice），延遲由 deadline 決定，和權重分開：

    d_i = v_i + r_i \times \frac{1024}{w_i}

    延遲靠 heuristics 撐著

    既然延遲沒有參數，CFS 只能在周邊補規則。下表比較 CFS 的最後一版 v6.5 和 v6.6 的 kernel/sched/features.h 與 fair.c（兩版都在本站的 kernel-src/ 裡）：

    v6.5 的機制做什麼v6.6
    喚醒補償 + GENTLE_FAIR_SLEEPERS醒來的 task 放到 min_vruntime 減 sysctl_sched_latency 的一半移除，改成睡前存 lag、醒來還回去（PLACE_LAG）
    START_DEBIT新 task 先往右放一段，不讓它一來就插隊移除
    sysctl_sched_wakeup_granularity醒來的 task 要領先超過門檻才能搶占移除，改成重新挑一次、比 deadline
    sysctl_sched_latency、sysctl_sched_min_granularity、sched_nr_latency依 task 數算出 sched_slice()移除，一律用 sysctl_sched_base_slice（0.75ms）
    LAST_BUDDY搶占後優先讓剛被換下的 task 回來，為了 cache 區域性移除（NEXT_BUDDY 留著，預設關閉）

    這些規則各自都有道理，例如 v6.5 的註解寫 GENTLE_FAIR_SLEEPERS 是 “Only give sleepers 50% of their service deficit”。但它們疊在一起就很難分析：補償送多少、門檻設多大，都是調出來的經驗值，彼此還會互相影響。光是喚醒補償，從 v2.6.24 的 20ms 到 v6.5 的 6\,\text{ms} \times \tfrac{1}{2} = 3\,\text{ms}（單核時），數字就一路在變。

    本站量到的結果也說明了這種補償有多粗：情境 2 跑 1 秒，CFS v2.6.24 下 editor 相對 GPS 的 lag 累積到 −75.6ms，而且 editor 第一次長睡之後，每次醒來都貼著 −20ms 的上限，短睡也一樣。補償不管 task 睡前是被欠還是多拿，一律照送。Zijlstra 在第一版 EEVDF patch 的 cover letter 寫的就是想刪掉這些程式碼：“if we can pull this off we can delete a whole much of icky heuristics code”。最後合併的 commit「sched/fair: Commit to EEVDF」只有兩句說明：

    EEVDF is a better defined scheduling policy, as a result it has less heuristics/tunables. There is no compelling reason to keep CFS around.

    先試過的路：latency-nice

    在 EEVDF 之前，社群已經有一套讓 task 表達延遲需求的 patch：Parth Shah 加入 per-task 的 latency-nice 屬性，Vincent Guittot 加入 latency_offset，讓延遲敏感的 task 醒來時可以插隊。這套 patch 能用，但做法是在 CFS 旁邊再維護一棵依延遲排序的樹。Zijlstra 的回應是：

    Ever since looking at the latency-nice patches, I've wondered if EEVDF would not make more sense

    他在同一封信裡也直說 “I really dislike the dual tree”，不喜歡為了延遲另外維護一棵樹。

    他的判斷是：與其在只有一個參數的 CFS 外面再加一層延遲機制，不如換成本來就有兩個參數的演算法。EEVDF 出自 1995 年 Stoica 與 Abdel-Wahab 的論文，lag 有證明過的上下界（），搶占的規則也前後一致：tick 時看 slice 用完沒，喚醒時重新挑一次看 deadline（），不再需要 wakeup granularity 這類門檻。

    代價：真正的公平讓一些 workload 變慢

    換掉 heuristics 不是沒有代價。第二版 patch 原本想保留類似 sleeper bonus 的放置方式（PLACE_BONUS），Zijlstra 形容它是 “a mixed bag of pain”：EEVDF 照權重算，一個 100% 忙碌的 parent 和一個 50% 忙碌的 child 會分到 67% / 33%，而 CFS 的 sleeper bonus 讓它們拿到 50% / 50%。stress-futex、stress-nanosleep 這類 benchmark 原本受惠於 CFS 多送的那份 CPU，換成 EEVDF 就變慢；可是保留 bonus，又會把 task 放得太靠左，弄壞 hackbench 和 latency-nice。最後 bonus 沒有留下。

    各方的測試結果也是有贏有輸。Chen Yu 量到 schbench 的 95 百分位延遲降了七、八成；IBM 的 Shrikanth Hegde 在 POWER 上量到 daytrader 的吞吐量多了 7%～9%，但「4 X Shell Scripts」少了 53%，他自己標註 “This is a concerning one.”。第三版的 cover letter 總結是 “what was found was better latency and smaller variance”。也就是說，延遲和穩定度變好了，部分仰賴 sleeper 補償的吞吐量型 workload 付了代價，這和的取捨是同一件事。

    介面：從 latency-nice 到 slice

    第三版時有人反對 latency-nice 這個介面，Zijlstra 改提「直接讓 task 宣告 slice 長度」，用 sched_attr::sched_runtime 傳進來。v6.6 合併的是沒有這個介面的版本，所以 v6.6 裡大家的 slice 都是 0.75ms，會看到這讓 audio 的 deadline 不會比較早。per-task slice 要到 v6.12 才進來，而且光有它還不夠，要同時補上 PREEMPT_SHORT 和 DELAY_DEQUEUE，短 slice 才有效果（）。

    CFS 用一個 vruntime 同時處理公平與延遲，但這兩者其實是不同的需求。v6.6 引入的 EEVDF 把它們拆開：公平交給 lag，延遲交給 deadline。它同樣使用 vruntime，先看 lag 怎麼從 vruntime 算出來。

    從 lag 到 V

    的 lag 是 S_i - s_i，兩個量都是 CPU 時間。把它們換成和 vruntime 一樣的單位，就能直接比較。task 實際拿到的時間 s_i 換算之後就是 vruntime（\Delta v_i = \Delta t \times 1024 / w_i）：

    s_i = \frac{w_i}{1024}\, v_i

    GPS 這邊也一樣。GPS 讓每個想執行的 task 同時以 w_i / W 的速度拿 CPU，換算成 vruntime，大家都以同一個速度 1024 / W 前進。把這個共同的 vruntime 記為 V（虛擬時間），GPS 應給的時間就是

    S_i = \frac{w_i}{1024}\, V

    兩式相減，lag 只剩 V 和 v_i 的差：

    \text{lag}_i = S_i - s_i = \frac{w_i}{1024}\,(V - v_i)

    所以 lag 的正負只看 task 的 vruntime 落在 V 的哪一邊：在左邊就是被欠，在右邊就是多拿。lag ≥ 0 的 task 稱為 eligible，只有 eligible 的 task 可以被選：

    \text{lag}_i \ge 0 \quad\Longleftrightarrow\quad v_i \le V

    剩下的問題是 V 怎麼求。kernel 不會另外跑一個 GPS，而是利用推過的「所有 lag 加起來是 0」：

    \sum_j w_j\,(V - v_j) = 0 \quad\Longrightarrow\quad V = \frac{\sum_j w_j\, v_j}{\sum_j w_j}

    也就是所有 runnable task 的 vruntime 依權重的平均，由 avg_vruntime() 計算。

    deadline：eligible 之中誰先

    第二個量是 deadline。slice 是 task 一次想連續執行的長度，deadline 等於 vruntime 加上 slice 換算成的虛擬時間，換算方式和 vruntime 相同：

    d_i = v_i + \text{slice}_i \times \frac{1024}{w_i}

    挑選規則是：在 eligible 的 task 中，選 deadline 最早的。

    \text{pick} = \mathop{\arg\min}_{i \,:\, v_i \le V} \; d_i

    把下圖的預設值代進去。三個 task 都是 nice 0，所以 1024 / w_i = 1，V 就是 vruntime 的平均：

    V = \frac{-0.30 + 0.35 - 0.05}{3} = 0
    taskv_ieligible（v_i \le V）\text{slice}_id_i
    A−0.30是0.750.45
    B+0.35否0.751.10
    C−0.05是0.300.25（最早，選中）

    單位都是 ms。A、C 是 eligible，其中 C 的 deadline 最早，所以選 C。B 不 eligible，deadline 再早也不會被選。

    把 C 的 slice 拉到 0.5ms 以上，被選中的就會換成 A；把 B 的 slice 拉到最短，B 依然不能被選，因為它不 eligible。再連按幾次「跑完 slice」，會發現 slice 短的 C 輪到的次數比較多，但每次只執行一小段。

    簡化：三個 task 都是 nice 0，所以 V 就是 vruntime 的平均；調整 slice 時 deadline 會立刻重算，實際的 kernel 要等到下一次 request 才會更新。

    深入：kernel 的 V 和 GPS 的 V 什麼時候不一樣

    v6.6 kernel/sched/fair.c 的註解寫的是

    \text{lag}_i = S - s_i = w_i \cdot (V - v_i)

    它把權重當成單純的比重，沒有除以 1024，單位是「權重 × 時間」；除以 nice 0 的權重 1024 就換回時間，也就是本站圖上的單位。不管哪種單位，正負號都只看 V - v_i。

    上面用加權平均求 V，前提是 runqueue 上所有 task 的 lag 加起來剛好是 0。task 帶著不為 0 的 lag 加入或離開，總和就不再是 0，加權平均和 GPS 真正的 V 就分開了。註解自己也寫了：只有 task 都在 lag = 0 時進出，這兩者才相等。模擬頁上的 lag 是另外照定義算的 GPS，不是 kernel 的 vlag，所以可以拿來檢查 kernel 的近似差多少。

    跑完一個 slice：update_deadline()

    被選中的 task 一路執行，vruntime 往右走。走到 deadline 時，表示這次要求的 slice 用完了，update_deadline() 給它下一個 deadline，並要求重新挑選：

    v_i \ge d_i \quad\Longrightarrow\quad d_i \leftarrow v_i + \text{slice}_i \times \frac{1024}{w_i}

    一個一直有事做的 task 就這樣每 0.75ms 換一次 deadline。它的 vruntime 也同時越過 V，變成不 eligible，讓給其他 task。

    醒來放在哪裡：place_entity()

    CFS 醒來時一律放在 min_vruntime − 20ms 附近（），不管 task 睡前是被欠還是多拿。EEVDF 改成照帳本放：task 離開 runqueue 時，update_entity_lag() 記下它的 lag（vlag，以 vruntime 為單位）；回來時 place_entity() 把它放回 V 左邊同樣的距離，deadline 從那裡重新算起。這就是 sched_feat 裡的 PLACE_LAG：

    \texttt{vlag} = V - v_i \;\;\text{（離開時）}, \qquad v_i \leftarrow V - \texttt{vlag},\quad d_i \leftarrow v_i + \text{slice}_i \times \frac{1024}{w_i} \;\;\text{（回來時）}

    睡覺不會讓被欠的消失，也不會讓多拿的一筆勾銷。這裡有兩個細節。

    第一，vlag 有上下限。nice 0、slice 0.75ms、tick 1ms 時，上限是 1.5ms：

    \texttt{vlag} \leftarrow \operatorname{clamp}\bigl(V - v_i,\; -L,\; L\bigr), \qquad L = \max(2 \times \text{slice},\; \text{TICK}) \times \frac{1024}{w_i}

    被欠再多，最多也只帶回 1.5ms。論文裡的 lag 上下界是證明出來的性質（見下面的深入），kernel 則是直接截斷，免得一個 task 帶著極端的 lag 回來。

    第二，task 一加入就會拉動 V。V 是加權平均，加入一個在 V 左邊的 task，平均就往左移，它的 lag 跟著縮水。所以 place_entity() 先把 lag 放大再放：

    v_i \leftarrow V - \texttt{vlag} \times \frac{W + w_i}{W}

    W 是加入前 runqueue 上的權重總和。舉個例子：cc1、cc2 在 runqueue 上（W = 2048），audio（w = 1024）帶著 \texttt{vlag} = +0.3 回來。

    深入：lag 最多能偏多少，論文的上下界

    EEVDF 每次讓一個 task 連續執行 slice 那麼久，lag 的鋸齒高度就由 slice 決定（：連續執行 q，lag 下降 q\,(1 - w_i/W)）。Stoica 與 Abdel-Wahab 的論文證明，lag 的上下界和 request 大小有關：

    -r_{\max} \;<\; \text{lag}_i \;<\; \max(r_{\max},\, q)

    r_{\max} 是最大的 request（一次要求的執行長度，也就是 slice），q 是排程的時間單位。模擬裡 0.75ms 的 slice 會被 1ms 的 tick 放大成 1ms（tick 時才檢查有沒有用完），量到的 lag 都在 ±1ms 內，符合這個上下界。兩個 nice 0 的 hog 在 CFS v2.6.24 下一次跑一整段 sched_slice()（約 10ms），lag 擺到 5ms 以上；EEVDF 只擺 0.5ms 左右。

    深入：論文的演算法和 kernel 差在哪

    Stoica 與 Abdel-Wahab 的論文定義的是一個理想的演算法：V 照 dV/dt = 1/W 精確累加；每個 task 有一個 request，從 virtual eligible time v_e 開始、到 virtual deadline v_d = v_e + r/w 結束；每一個 quantum q 分給 eligible（v_e \le V）的 request 裡 v_d 最早的。task 離開與加入時，論文用兩條式子調整 V：

    \text{離開：}\; V \leftarrow V + \frac{\text{lag}_j}{\sum_{\text{離開後}} w_i}, \qquad \text{加入：}\; V \leftarrow V - \frac{\text{lag}_j}{\sum_{\text{加入後}} w_i}

    這兩條式子讓所有 task 的 lag 總和一直是 0，也就是 \sum w_i (V - v_i) = 0，移項就得到 V = \sum w_i v_i / W。所以論文的 V 和 kernel 的 avg_vruntime() 在精確的算術下是同一個量，kernel 只是改成直接算加權平均，再加上整數運算的截斷。

    加入的那條式子分母包含加入者自己，所以帶著 lag \ell 回來的 task，自己也分攤了一份，實際只帶回 \ell \cdot W/(W + w_i)。上面表格「直接放」的那一列就是論文的結果；kernel 的 place_entity() 刻意放大 (W + w_i)/W 把這一份補回來，註解寫的理由是 “otherwise lag can quickly evaporate”。拿情境 4 來看，audio 每次帶著約 −0.21ms 的 lag 去睡：論文只帶回三分之二，醒來最久等 420µs（0.14 \div \tfrac{1}{3}）；kernel v6.6 整筆帶回，平均要等 623µs。

    v6.6 還做不到的事

    v6.6 所有 task 的 slice 都固定為 sysctl_sched_base_slice（0.75ms），deadline 拉不開，CPU scheduler 無從得知誰比較急。再加上 lag 會原樣帶回，剛執行完一段就去 sleep 的 task，醒來時多半帶著負的 lag，不 eligible，還得再等一下。這兩件事合起來，就是 v6.12 要解決的問題（）。

    前面談的都是「挑誰」，另一個同樣重要的問題是「什麼時候挑」。回到的狀態圖，task 離開 CPU 有兩種方式：自己去睡，或是被換下。只在第一種情況才重新挑選的 CPU scheduler 稱為 non-preemptive，一個不睡覺的 CPU-bound task 拿到 CPU 後就不會交出來（Windows 3.x 和 Mac OS 9 以前的 cooperative multitasking 就是這樣，一個程式卡在迴圈裡，整台電腦跟著卡住）。允許把 CPU 從正在執行的 task 手上拿走的，稱為 preemptive。

    CFS 的 WAKEUP_PREEMPT

    CFS 喚醒時的條件（check_preempt_wakeup()）是

    v_{\text{curr}} - v_{\text{wakee}} > \text{gran}, \qquad \text{gran} = 10\,\text{ms} \times \frac{1024}{w_{\text{curr}}}

    也就是醒來的 task 的 vruntime 要比 curr 小超過 10ms（sysctl_sched_wakeup_granularity，依 curr 的權重換算）才能插隊。設門檻是為了不讓「只落後一點點」的 task 頻繁打斷 curr。喚醒補償把醒來的 task 放到 min_vruntime − 20ms，通常就超過這個門檻，所以 interactive task 醒來多半能立刻執行。

    WAKEUP_PREEMPT 關掉的就是這一條，但 CFS 並不會因此變成 non-preemptive：tick 的檢查還在，只是醒來的 task 必須等到 curr 用完 sched_slice()。在模擬頁的「延遲和公平」情境（audio 每 5ms 醒來一次，另有兩個編譯 task cc1、cc2）關掉它，2 秒內的結果是：

    EEVDF 的 RUN_TO_PARITY

    EEVDF 的喚醒搶占沒有固定門檻，而是直接問挑選規則：如果現在重新挑，pick_eevdf() 會不會選醒來的 task？會，就搶占。規則前後一致，但 curr 可能才跑一小段，就因為一個 deadline 更早的 task 醒來而被換下。RUN_TO_PARITY 的做法是：curr 被選中後，只要還 eligible，就讓它把這個 slice 跑完，期間不重新比 deadline。

    在模擬頁關掉 RUN_TO_PARITY，結果幾乎不變（context switch 1881 → 1871，audio 的延遲完全一樣）。原因是 v6.6 每個 task 的 slice 都是 0.75ms：curr 是在 eligible 時被選中的，deadline 最多是 V + 0.75；醒來的 task 若 lag 不大，被放在 V 附近，deadline 也在 V + 0.75 附近，就算重新比，多半還是 curr 的 deadline 比較早。這層保護真正擋下的，是 slice 比 curr 短的 task，所以 v6.12 讓 task 自訂 slice 時，同時加了 PREEMPT_SHORT：slice 比 curr 短的 task 醒來，可以取消 curr 的這層保護（）。

    第一關：curr 的保護與 PREEMPT_SHORT

    audio 醒來時，CPU 上通常是某個 cc。講過，RUN_TO_PARITY 讓 curr 把這次的 slice 跑完，中途有人醒來也不重新比 deadline。audio 的 deadline 再早，也得等 cc 跑完。

    PREEMPT_SHORT 讓 slice 比較短的 task 可以取消這層保護。do_preempt_short() 檢查的條件是（p 是醒來的 task，c 是 curr）：

    \text{slice}_p < \text{slice}_c \;\;\wedge\;\; p \text{ eligible} \;\;\wedge\;\; \bigl(d_p < d_c \;\vee\; c \text{ 不 eligible}\bigr)

    成立時，kernel 讓 curr 不再受 RUN_TO_PARITY 保護，立刻重新挑選。第一個條件說明了為什麼 audio 一定要宣告 slice：slice 和 cc 一樣是 0.75ms 的話，這條規則根本不會啟動。

    第二關：帶著負的 lag 醒來

    第二個條件「p eligible」才是真正卡住的地方。audio 每次跑 0.31ms，這段時間三個 nice 0 的 task 照 GPS 各應得三分之一，所以 audio 的 lag 下降

    \Delta\text{lag} = -\,0.31 \times \Bigl(1 - \frac{1}{3}\Bigr) \approx -0.21\ \text{ms}

    它帶著 −0.21ms 去睡。v6.6 的 PLACE_LAG（）把這筆帳存起來，醒來原樣放回 V 的右邊，audio 不 eligible，slice 再短也選不到它。它只能排隊，看著別人跑，lag 以 w_i / W = 1/3 的速度爬回 0：

    t_{\text{wait}} = \frac{|\text{lag}|}{w_i / W} = \frac{0.21}{1/3} \approx 0.62\ \text{ms}

    正好是表裡的 620µs。照帳本來說這不算錯：audio 剛剛確實多拿了，本來就該等別人追上來。問題出在時機。audio 一睡就是 4.73ms，別人早就追上來了，可是帳本在它睡著時凍結，這段時間沒有算進去。

    DELAY_DEQUEUE 讓帳本在睡著時繼續算。task 去睡時如果不 eligible，dequeue_entity() 先不把它移出 runqueue，只標記為 sched_delayed，讓它留在樹上繼續參與競爭。它不會真的執行，但 V 繼續往前，它的 lag 跟著往上爬。等到它被 pick_eevdf() 選中，lag 一定已經 ≥ 0，kernel 這時才真正把它移出，DELAY_ZERO 再把正的 lag 截成 0。kernel/sched/features.h 的說明是：

    By delaying the dequeue for non-eligible tasks, they remain in the competition and can burn off their negative lag. When they get selected they'll have positive lag by definition.

    audio 的 0.62ms 債，在 4.73ms 的睡眠一開始就還完了，醒來時 lag 是 0，eligible，兩關都過。勾選下面的開關，看 audio 一個週期內的 lag 怎麼走，以及醒來時卡在哪一個條件：

    先只開 custom slice 和 PREEMPT_SHORT（預設），audio 醒來時在 eligible 區域外面，要排 620µs。打開 DELAY_DEQUEUE，睡著後那一小段線會爬回 0，醒來就能馬上跑。再關掉 custom slice：lag 一樣是 0，卻因為 slice 不比 cc 短，照樣要等。

    代價：睡著時還的債，是誰付的

    三樣都有時，audio 拿到 6.15% 的 CPU，正好是它每個週期的全部需求 0.31 / (0.31 + 4.73)，比公平的份 5.49% 多；多出來的來自 cc1、cc2，各少約 0.3 個百分點。

    原因在於「睡著時還債」只是帳面上的。audio 留在 runqueue 上的那段時間，CPU 照樣全給 cc1、cc2 跑，它們並沒有因此多拿到什麼，只是 audio 的帳被改成了 0。用的 GPS（睡覺時 lag 不動）來看，audio 每個週期都被免掉約 0.21ms 的欠帳，模擬頁的 lag 圖上，它的線會一路往下。

    這和 CFS 的喚醒補償（）結果相近，CFS 下 audio 也拿到 6.06%，差別在規則。CFS 不管睡前的帳，醒來一律往左放一段；v6.12 只原諒負的 lag，而且是在 task 真正睡著、別人用得到 CPU 的時候才原諒。延遲靠 task 自己宣告的 slice 換到，不再靠 CPU scheduler 猜。會把這幾種做法放在一起，看延遲、公平、切換次數之間的取捨。到模擬頁看情境 4 →

    深入：被延後的 task 還在拉 V

    sched_delayed 的 task 仍然在樹上，它的權重也還算在 W 和 V 的加權平均裡。audio 延後離開的那 0.62ms，V 以 1024 / 3072 的速度前進，而不是只剩兩個 cc 時的 1024 / 2048，這正是 audio 的 lag 能以 1/3 的速度爬回 0 的原因。換句話說，它「還債」的速度，是照它仍在競爭時算的。

    v6.12 還修正了 fork 的放置：v6.6 的 PLACE_DEADLINE_INITIAL 想讓新 task 從半個 slice 開始，卻被之後的 activate_task() 再放一次而蓋掉；v6.12 讓 fork 的那次放置帶上 ENQUEUE_INITIAL，半個 slice 才真的生效。

    評估 CPU scheduler 的指標很多（CPU 使用率、throughput、turnaround time、waiting time、response time），它們無法同時做到最好，其中最常見的拉扯是 response time 和 throughput。本站量的「喚醒延遲」，也就是 task 醒來到真正開始執行的時間，屬於 response time。

    拉扯的來源是 context switch 的成本。每次換人，kernel 要保存與載入暫存器、執行一次排程邏輯，這是直接成本；更大的往往是間接成本：新上來的 task 要用的資料不在 cache 裡，TLB 也要重新填，前一小段時間會跑得比較慢。以 Round Robin 為例，設 time slice 是 q，每次切換的成本是 c，n 個 task 輪流執行：

    \text{用在工作上的比例} = \frac{q}{q + c}, \qquad \text{醒來後最久要等} \approx (n - 1)(q + c)

    q 越小，醒來的 task 越快輪到，但切換越頻繁，花在 c 上的比例越高；q 越大則相反。假設 c = 5\,\mu\text{s}、n = 3（c 只是為了看出量級的假設值，實際的間接成本依工作負載差很多）：

    q用在工作上的比例醒來後最久要等
    0.1 ms95.2%0.21 ms
    0.75 ms（EEVDF 預設 slice）99.3%1.51 ms
    6.7 ms（CFS 三個 task 時的 sched_slice）99.93%13.4 ms

    深入：sleep 時 lag 怎麼算，為什麼 CFS 和 v6.12 的 audio 多拿

    的 GPS 在 task sleep 時不分 CPU 給它，lag 停在睡前的值，醒來接著算；照這個算法，睡覺不會讓欠帳消失。v6.6 也是這樣做的，睡前把 lag 存進 vlag，醒來放回去。

    CFS 和 v6.12 在這裡和 GPS 不一樣。CFS 讓剛醒的 task 從 min_vruntime − sched_latency 開始，等於每次醒來都送它一段時間。v6.12 的 DELAY_DEQUEUE 讓 lag 為負的 task 睡著後還留在 runqueue 上，慢慢把負的 lag 還掉，醒來時 lag 大約是 0。從「睡覺時 lag 不變」的角度看，這兩種都等於把欠帳免了，所以圖上它們的 audio、editor 會一路往下。如果改成「睡覺就把負的 lag 清掉」，v6.12 看起來會是公平的。論文對帶著 lag 離開的 task 有幾種處理方式，這部分之後會再對照原文。

    模擬器不計 context switch 的成本，切換是瞬間完成的，所以 CPU 比例不會因為切換變多而下降。看模擬結果時，請把 context switch 次數當作吞吐量成本的指標；CPU 比例反映的是公平，不是吞吐量。

    開頭的問題是：只有一顆 CPU，該讓誰先執行？拆開來其實是兩個問題，長期下來每個 task 該分到多少（公平），以及醒來之後多快輪到它（延遲）。這一章把各代的答案放在一起看。

    挑選規則，一行就寫得完

    每一代挑下一個 task 的規則都很短，差別在比的是什麼：

    \begin{aligned} \text{2.4：}\; & \max_i \; \text{goodness}_i = \text{counter}_i + 20 - \text{nice}_i \\ \text{2.6.0：}\; & \min_i \; \text{prio}_i = \texttt{static\_prio}_i - \text{bonus}_i \\ \text{CFS：}\; & \min_i \; v_i, \qquad v_i \mathrel{+}= \Delta t \cdot \tfrac{1024}{w_i} \\ \text{EEVDF：}\; & \min_{v_i \le V} \; d_i, \qquad d_i = v_i + r_i \cdot \tfrac{1024}{w_i} \end{aligned}

    2.4 和 2.6.0 把「該分多少」和「該多快」混在同一個數字裡：goodness 和 prio 同時決定誰先跑，而時間片的長短又決定比例。CFS 只留下公平，v_i 齊頭並進就是照權重分（），延遲沒有自己的參數，只能靠喚醒時的補償。EEVDF 多了第二個參數 r_i：w_i 決定長期拿多少，r_i 決定 deadline 有多早，兩件事終於分開了。

    誰在意延遲：從猜到說

    怎麼知道誰在意延遲給它什麼本站量到的代價
    O(n) 2.4不分辨。睡著時遇到重算的 task，沒用完的 counter 保留一半goodness 較高，醒來能插隊每次挑選都要走過整條 runqueue（）
    O(1) 2.6.0猜：sleep_avg 越高越像 interactive優先權最多 +5，時間片用完還能留在這一輪跑 2.3ms 睡 0.83ms 的 cheat 拿走 67.0%，公平的份是 29.8%
    CFS v2.6.24不分辨，每個醒來的 task 都補放在 min_vruntime − sched_latency，通常能立刻搶占audio 拿 6.06%，比公平的份 5.49% 多；lag 沒有上界
    EEVDF v6.6不分辨，也不補，照 lag 的帳放回去lag ≥ 0 才 eligible；所有 task 的 slice 都一樣audio 醒來平均等 623µs

    從上往下看，CPU scheduler 越來越不靠猜測來認識 task。O(1) 的問題不在猜得不夠準，而是只要從行為去猜，就有人能照著規則演出來（）。CFS 乾脆不猜，每個醒來的 task 都補一樣多，公平因此打了折扣。EEVDF 先把帳算清楚，再讓 task 自己把需求說出來。代價是應用程式得配合：沒有呼叫 sched_setattr() 的 editor，在 v6.12 下平均還是要等 503µs，和 v6.6 的 608µs 差不多（情境 2）。

    理論和實作的距離

    每一代都可以拿 GPS 量一次離公平有多遠（）。O(n) 和 O(1) 本來就不是照比例分享設計的，在 O(1) 下 nice 差一級的效果，會隨起點的 nice 而變（）。CFS 長期的比例很準，但一次跑一整段 sched_slice()，短時間內 lag 擺得大，喚醒補償還讓 interactive task 的 lag 沒有上界。EEVDF 有論文證明的上下界，但 kernel 的實作和論文之間仍有距離：tick 讓 0.75ms 的 slice 變成 1ms、lag 被截斷、重新加入時刻意保留整筆 lag（的深入）。

    這些距離多半是工程上的取捨，不是錯誤。HRTICK 預設關閉，只在 tick 檢查 slice，省下高精度計時器的成本；截斷 lag，是不讓睡了很久的 task 帶著極端的帳回來；保留整筆 lag，則是不想讓帳越算越少。的延遲與吞吐量，也是同一類取捨。

    之後：sched_ext

    v6.12 同時合併了 sched_ext（extensible scheduler class）。它不是另一個演算法，而是一個介面：使用者用 BPF 寫一組 callback，實作 struct sched_ext_ops，在系統執行中載入，就能接手 SCHED_NORMAL、SCHED_BATCH、SCHED_IDLE 與 SCHED_EXT 的 task；設了 SCX_OPS_SWITCH_PARTIAL 時只接手 SCHED_EXT 的。唯一必填的欄位是 ops.name，其他 callback 都可以省略。

    BPF 排程器和 kernel 之間用 dispatch queue（DSQ）溝通。每顆 CPU 有一個 local DSQ（SCX_DSQ_LOCAL），另外有一個全域的 SCX_DSQ_GLOBAL。task 醒來時先呼叫 ops.select_cpu() 挑 CPU，再呼叫 ops.enqueue()，BPF 程式可以直接把它放進某個 DSQ，也可以先留在自己的資料結構裡。CPU 要找下一個 task 時，先看自己的 local DSQ，再看 global DSQ，都空了才呼叫 ops.dispatch() 補貨。DSQ 預設是 FIFO，改用 scx_bpf_dispatch_vtime() 放進自訂的 DSQ，就成了照 vtime 排序的優先佇列，前面幾章的 vruntime 與 deadline 都能在 BPF 裡重新實作。

    為了不讓一個寫錯的 BPF 程式拖垮系統，kernel 留了退路：BPF 排程器出錯、有 runnable task 太久沒被排到（watchdog，ops.timeout_ms 沒設定時是 30 秒），或使用者按下 SysRq-S，都會中止 BPF 排程器，所有 task 回到內建的 fair class（文件裡仍稱為 CFS，v6.12 實際上是 EEVDF）。文件也寫明 sched_ext 提供給 BPF 的介面沒有穩定性保證，可能隨版本改變。

    演進走到這裡，問題從「哪一個演算法最好」變成「讓每個系統換上適合自己的演算法」。本站不實作 sched_ext：它的用武之地在多核、cgroup 與特定的 workload，正好是本站刻意略過的範圍。

    sched_ext 的出處：v6.12 的 Documentation/scheduler/sched-ext.rst，watchdog 的預設值見 kernel/sched/ext.c 的 SCX_WATCHDOG_MAX_TIMEOUT（30 × HZ）。

## 讀原始碼時卡住的地方

- **goodness 的 +1 給誰。** `goodness(p, this_cpu, prev->active_mm)` 對「和 prev 同一個 mm」的 task 加 1。每個 user process 有自己的 mm，所以實際上就是 prev 自己。prev 是 idle 時，`active_mm` 是 idle 借來的（lazy TLB），也就是上一個跑過的 user task。模擬器用 `last_mm` 記這件事。
- **`reschedule_idle()` 的門檻是「高出 2 以上」**（`preemption_goodness() > 1`），而且 curr 用自己的 mm 算，多 1 分。所以醒來的 task counter 要比 curr 多 2 以上才搶得到。
- **平手時留下 prev。** `still_running` 先拿 prev 的 goodness 當候選，掃描時用嚴格的 `>`，所以平手的話 prev 繼續跑；prev 去睡時，平手取串列裡前面的（`add_to_runqueue()` 加在頭，所以是最近醒來的）。
- **重算的是 `for_each_task`，不是 runqueue。** `recalculate:` 走過系統裡每一個 task，睡著的也算：`counter = counter / 2 + NICE_TO_TICKS(nice)`。睡著的 task 沒用完的 counter 保留一半，反覆重算後收斂到 11（nice 0），將近兩倍。這是 2.4 唯一的互動性機制。模擬器加了一個 `for_each_task` 開關（kernel 沒有），關掉時只重算 runqueue 上的，用來看少了這行會怎樣：情境 4 的 audio 從 5.6% 掉到 0.26%，平均喚醒延遲 115ms。
- **成本。** 每次 `schedule()` 呼叫 goodness() n + 1 次（prev 先一次，再掃整條串列），重算時再加系統裡的 task 數。測試：64 個 hog 時每次挑選約 68 次操作，O(1) 2.6.0 約 3.5 次（`sched_find_first_bit()` 算 1 次，加上 enqueue / dequeue）。

## tick 記帳與 tick dodging

counter 只在 tick 扣，扣給 tick 當下在 CPU 上的 task。週期剛好是 10ms、每次在 tick 前睡著的 task 永遠不被扣：

| cheat 的行為 | O(n) 2.4.0（HZ = 100） | O(1) 2.6.0 | CFS v2.6.24 |
|---|---|---|---|
| 跑 9.4ms 睡 0.6ms | **86.5%** | 65.8% | 32.8% |
| 跑 2.3ms 睡 0.83ms（情境 3） | 12.2% | 67.0% | 32.7% |

（另兩個是 hog，2 秒。）這是 Tsafrir 等人 2007 年的 "Secretly Monopolizing the CPU Without Superuser Privileges" 描述的攻擊。比較情境的原則是不對齊 tick，所以這組只放在測試（`tick dodging`），沒有做成情境。如果要做，記得說明它是刻意對齊的。

情境 3 的 cheat 在 2.4 反而吃虧：醒來時 counter 比 cc 多（7–8 對 6，睡著時遇到重算），106 次喚醒裡 78 次搶到；但它每跑 2.3ms 就有 tick 扣 counter，幾輪就扣完，之後 goodness 是 0，要等兩個 cc 各用完 60ms、一起重算。

## 沒有實作

SMP（`PROC_CHANGE_PENALTY`、找閒置 CPU）、RT（`SCHED_FIFO` / `SCHED_RR`）、`SCHED_YIELD`、`schedule_timeout()`。fork 假設 parent 的 counter 是滿的 `NICE_TO_TICKS(nice)`。

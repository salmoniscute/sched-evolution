程式：`src/sched/o1-v2.6.0.ts`，測試：`test/o1-v2.6.0.test.ts`。

## 讀原始碼時卡住的地方

- **時間片是 tick 計，sleep_avg 是 ns 計。** `scheduler_tick()` 每個 tick 對 curr 的 `time_slice` 扣 1，不管這個 tick 裡它實際跑了多久；`sleep_avg` 卻是用 `sched_clock()` 的 ns 差算的。兩套時間並存，tick dodging 只能躲掉前者。
- **`schedule()` 的 `prev->sleep_avg -= run_time` 在挑完 next 之後才做。** 模擬器把它搬到 `put_prev_task`（挑選之前）。挑選只讀 next 的 sleep_avg，而 next 和 prev 是同一個時 `activated` 一定是 0，不會重算，所以順序不影響結果。
- **醒來後在 runqueue 上等的時間也算睡眠。** `activate_task()` 把 `timestamp` 設成醒來的時刻，被挑中時（`activated > 0`）再呼叫一次 `recalc_task_prio(next, timestamp + delta)`。被中斷叫醒的（`activated = 2`）全額算，被別的 process 叫醒的（1）打 30%（`ON_RUNQUEUE_WEIGHT * 128 / 100 = 38`，再除 128）。模擬器的喚醒都來自計時器，在 softirq 裡，`in_interrupt()` 成立，所以一律是 2（`wake_from_interrupt` 可以改）。
- **i386 的 32 位元溢位。** `recalc_task_prio()` 的 `sleep_time` 是 `unsigned long`，`sleep_time *= (MAX_BONUS - CURRENT_BONUS(p)) ? : 1` 最多乘 10。sleep_avg 接近 0、又睡了 430ms 到 815ms 之間時，乘出來超過 2³²，會繞回去：睡 500ms 的 task 在 64 位元上 sleep_avg 會被截在 1020ms，在 32 位元上只拿到約 705ms。模擬器預設 `bits_per_long: 32`，測試有一條專門驗這個。
- **fork 沒有真的 parent。** 工作負載的 task 都在 t = 0 附近建立。kernel 裡 child 是 parent 的複本：sleep_avg 從 parent 繼承再打 95 折，時間片是 parent 剩下的一半。模擬器假設 parent 是一個 sleep_avg 滿的 shell（`parent_sleep_avg: 'max'`），所以每個新 task 一開始 sleep_avg = 918ms、bonus +4、時間片 51 個 tick。這會影響前一秒左右：
  - 情境 2、4 的 editor / audio 最久的那幾次等待（31ms、35ms）都發生在前 50ms：cc 剛 fork 出來也是 bonus +4，editor 搶不贏。
  - 情境 5 的 2 秒比例是 45 : 33 : 21，純時間片比例（`parent_sleep_avg: 0` 或關掉 `sleep_avg`）是 41.5 : 33.1 : 25.4。
  - kernel 在 parent 在 runqueue 上時，讓 child 沿用 parent 的 prio、排在 parent 旁邊；模擬器一律走 `__activate_task()`。
- **`EXPIRED_STARVING` 的門檻和 nr_running 成正比。** `STARVATION_LIMIT * nr_running + 1` jiffies，三個 task 時約 3.06 秒，比 2 秒的模擬還長，所以四個情境裡關掉它都完全不變。

## 比較情境 3：cheat

cheat 每跑 2.3ms 睡 0.83ms（週期 3.13ms，不對齊 tick），另外兩個 hog。2 秒：

| 排程器 | cheat | cc1 | cc2 |
|---|---|---|---|
| GPS | 29.8% | 35.1% | 35.1% |
| O(n) 2.4.0 | 12.2% | 41.9% | 45.9% |
| O(1) 2.6.0 | **67.0%** | 15.4% | 17.7% |
| O(1)，關掉 TASK_INTERACTIVE | 33.7% | 33.2% | 33.1% |
| O(1)，關掉 sleep_avg | 1.3% | 50.3% | 48.5% |
| CFS v2.6.24 | 32.7% | 33.6% | 33.7% |
| EEVDF v6.6 | 29.8% | 35.1% | 35.1% |

- cheat 的 sleep_avg 在 890ms 上下（CURRENT_BONUS 8，bonus +3，prio 117）。每次睡 0.83ms 乘 (10 − 8) = 1.66ms，跑 2.3ms 扣 2.3ms，還在慢慢往下（從 fork 時的 918ms），長期會停在 CURRENT_BONUS 7（bonus +2，prio 118），還是互動型。10 秒的模擬 cheat 拿 72%。
- 被騙走的是「互動型用完時間片還能留在 active」：關掉 `TASK_INTERACTIVE` 就回到三等分。
- 但關掉 `sleep_avg` 也不是答案：沒有 bonus 時，會睡覺的 task 每次醒來都排在同優先權的 hog 後面等一整個時間片（約 100ms），情境 4 的 audio 平均要等 189ms、只拿 0.17%。O(1) 照顧互動型程式的手段只有這一個，所以只能繼續補規則（`interactive_credit`、`JUST_INTERACTIVE_SLEEP`、`activated = -1`……），規則越補越多，這是 CFS 取代它的背景。
- 也試過 tick dodging（跑 0.93ms 睡 0.07ms，每次在 tick 前睡著）：O(1) 下 cheat 拿 71%，和不躲 tick 差不多，因為它本來就靠 bonus 贏。tick dodging 對 2.4 的效果比較明顯，見 `notes/08`。

## 沒有實作

SMP / NUMA load balancing、RT、`sched_exit()` 把時間片還給 parent、`TASK_UNINTERRUPTIBLE`（`activated = -1` 的分支有寫，但工作負載不會走到）、`set_user_nice()`、`sched_yield()`。
